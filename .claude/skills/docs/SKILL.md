# Docs

retro_rt is a runtime other projects build on, and much of the code that uses
it is written by models that see one crate at a time. The docs are how they
learn what is true about it without reading every file. Two layers, kept in
step:

- **rustdoc** on the code: what each item is, its units and ranges, what it
  does not do. The authority on one item.
- **`docs/`**: one page per crate, plus the conventions every crate shares
  and guides for whole tasks. The authority on how items fit together.

The worklog (see the `worklog` skill) is the third, separate thing: *how we
found out* and *why*. Docs say *what is true*, flatly, in final form. When a
worklog entry settles a design, the same session updates the docs it touches.

Start a session at `docs/README.md`: it is generated, lists every crate with
its one-line description and every page with its status, and is the map.

## Layout

```
docs/README.md                generated by `cargo run -q -p rrt-docs -- index`
docs/crates/<crate>.md        one page per crate under crates/, named exactly as the crate
docs/conventions/<name>.md    a rule several crates share: bit orders, units, colour, timing
docs/guides/<name>.md         how to do one task end to end
```

Filenames are lower-case and hyphenated, named after the thing: `pad.md`,
not `input-notes.md`. The sections are fixed in `crates/rrt-docs/src/main.rs`
(`SECTIONS`); a folder not listed there fails the check.

## Every page starts with front matter

```markdown
---
title: rrt-input, the host's pad
status: solid | partial | draft
crates: rrt-input, rrt-app
covers: rrt_input::Input::read, rrt_input::Buttons, rrt_input::Pad
worklog: 1, 4
---
```

`status` is the honesty knob and the most important field on the page:

| status | means |
| --- | --- |
| `solid` | every covered item is documented in rustdoc, tested, and behaves as the page says. Logic is tested in-process; what only a device can show (a GPU, a display, a sound card, a gamepad) has a test that runs on the device where one exists and skips with a note where not, or is named under an `On hardware` section with what was seen |
| `partial` | true as far as it goes; the `Gaps` section names what is untested or missing |
| `draft` | written ahead of verification - a plan or a mapping, not a description |

Downgrade the moment a test or a user finds the page wrong. A `solid` page
that is wrong costs more than no page.

`crates` lists crate names as under `crates/` (or `all`). `covers` lists the
public items the page describes, as Rust paths with the library name
(`rrt_gpu::Target::read_back`). `rrt-docs check` fails when the last segment
of any of them is no longer declared in that crate - so a rename breaks the
build of the docs, not a reader's trust. `worklog` (optional) lists the entry
numbers that settled the page.

## A crate page

Lead with what the crate is for and its entry points, so a reader can use it
from the first screen. Then:

````markdown
# rrt-thing

One paragraph: what it is, who calls it, the one type to start from.

## <How it works / the main type>

Tables for settings and fields (name, default, meaning). A fenced block for a
trait or a call sequence. Name the test that holds each behaviour:
`a_client_joins_talks_and_leaves`.

## Not here

What a reader might expect and will not find, and where it lives instead
(usually: in the game's own crate, because it encodes one console or one
game).

## Gaps

Untested paths, missing features, known limits - or "Nothing known." Never
leave this out: an empty one is a claim, a missing one is a silence. A page
with a gap is `partial`. Something left out on purpose is not a gap: it goes
under `Not here` with the reason, and the page can still be `solid`.
````

When a gap is found, close it - code and a test - rather than describing
it. Make the untestable part as small as possible: split the logic from the
device call (rrt-input's `compose`, rrt-audio's `mix_into`, rrt-app's
`key_action`) so only a few lines of glue need the device.

## A convention page

A rule more than one crate depends on: the pad's bit order, what a colour
value means, how ticks relate to frames, where versions are pinned. State the
rule, then the table of who converts how, then the tests that hold it. A
crate page links to the convention instead of restating it.

## A guide

A task from start to finish (start a game, move a port across), in numbered
steps, each with the code it takes. Guides cite crate pages for detail.

## Rustdoc on the code

This is what a model reads first, in the file it is editing. The house style
is hwtr's and piney_apples':

- **Every crate opens with `//!`** (checked): the first line says what it is
  as a noun phrase - "The host's pad, read once a frame." - then which types
  do what, with intra-doc links (`[`Input`]`, `[`Input::read`]`), then what
  is *not* here and where it lives, then the docs page:
  `See docs/crates/rrt-input.md.` Every module file opens the same way, one
  or two lines.
- **Every public item has a doc comment** (`missing_docs` warns). Say what
  the thing *is* or *does*, in the present tense, flatly: "Held buttons,
  active high, in the PlayStation pad's order." Not "This function will...".
- **Units, ranges and encodings on every field and parameter** where there
  is one: "0 left, 0x80 centre, 0xff right", "frames a second", "RGB 0-1",
  "u32 little-endian", "0 is taken as 1". Endianness said once per format.
- **Name the origin of a behaviour** when it is not obvious: which console
  behaviour it reproduces, which project it was lifted from, why the number is
  what it is ("A DualShock's potentiometers saturate before its round gate,
  so...").
- **Say what it does not do** on the item when a reader would assume it: "No
  dead zone is applied." "This blocks: call it from a menu."
- **`# Panics`** on anything that can panic, saying when. Errors say what the
  caller does with them ("the caller carries on silent").
- **Tests are named as sentences** stating the behaviour they hold
  (`falling_far_behind_drops_the_excess`), so a docs page can cite them and a
  failing test name reads as the broken claim.
- Comments inside functions explain *why*, not *what*: the quirk kept, the
  case handled, the reason for the order.
- Intra-doc links must resolve: `RUSTDOCFLAGS="-D warnings" cargo doc
  --workspace --no-deps` is part of finishing.

## Rules

- No emojis.
- Never write aspirational documentation as `solid` or `partial`. Docs
  describe the code as it is. A plan is `draft`, and says so in its first
  lines.
- Distinguish tested from believed: "Tests: `x`" is a measurement; "ported
  from hwtr-disc, where it reads a real disc" is evidence of a different
  kind - say which.
- Exact names. Item paths, field names, defaults and constants copied from
  the code, never paraphrased. A wrong default in the docs is worse than none.
- One subject per page. A page growing two splits.
- Cross-link with relative paths: `[the pad convention](../conventions/pad.md)`.
- Nothing console-specific belongs in the runtime or its docs except as a
  named convention (the pad's bit order). If a page starts describing one
  game's behaviour, that belongs in the game's repo.

## Finishing

When a public item changed, all of these, in order (CI, `.github/workflows/ci.yml`,
runs the same and fails on any warning):

```sh
cargo fmt --all
cargo clippy --workspace --all-targets          # no warnings
cargo test --workspace
RUSTDOCFLAGS="-D warnings" cargo doc --workspace --no-deps
cargo run -q -p rrt-docs -- index               # regenerate docs/README.md
cargo run -q -p rrt-docs -- check               # pages agree with the code
```

`check` catches a crate with no page, a page missing front matter, an unknown
status, a `covers` item that no longer exists, a dead relative link, a crate
without a `//!` header or the workspace lints, and a stale index.
